# AGENTS.md

This repository builds and publishes conda packages with `rattler-build` in
GitHub Actions. Your job is limited to adding a package or fixing a broken
package. Leave CI, release automation, scripts, versions, and unrelated
packages alone.

## Hard rules

- NEVER build locally. Do not run `rattler-build`, `conda-build`, a recipe's
  build/test scripts, or any `pixi` build task. Push a branch, open a pull
  request, and use the resulting GitHub Actions run as the build and test
  result.
- Do not edit any of these protected paths:
  - `.github/`
  - `scripts/`
  - `lucifer/`
  - `conda_build_config.yaml`
  - `pixi.toml`
  - `pixi.lock`
  - `rattler-config.toml`
  - `renovate.jsonc`
  - `ruff.toml`
  - `tombi.toml`
  - `typos.toml`
  - `AGENTS.md`

  The only exception is clear, strong evidence that the protected file itself
  is causing the failure, such as a failing command and log path that directly
  identify it. Stop, show that evidence, and ask the owner before changing a
  protected file.
- Do not hand-edit an existing package's version or build number. The scheduled
  `update` workflow owns version updates and build-number resets. An initial
  upstream version may be set once when adding a new package; after that, use
  the existing `extra.update` automation.
- Follow the closest existing package. Do not introduce a new layout, tool,
  build system, script style, or dependency workflow.
- Change only the target package under `packages/<name>/` and, when needed,
  that package's row in `packages.csv`. Do not clean up or "improve" unrelated
  files.
- Do not merge a pull request or push directly to `main`. Do not manually
  trigger publishing or run `scripts/publish.*`.

## Repository layout

- `packages/<name>/recipe.yaml` is the package's `rattler-build` recipe.
  `recipe.yaml` may reference additional files in the same directory, such as
  `build.sh`, `build.ps1`, `CMakeLists.txt`, downloader scripts, JSON metadata,
  or platform-specific assets.
- `packages.csv` is the build matrix. Each active row is
  `pkg,win-64,osx-arm64,linux-64,linux-aarch64,noarch`. The `pkg` value must
  match an active directory at `packages/<pkg>/`.
- A non-empty platform cell selects a GitHub runner and schedules that
  platform build. Blank means that platform is not built. For `noarch`, set the
  runner in the `noarch` column and leave the four platform columns blank.
- A matrix value shaped `runner+container` means use that runner with
  `ghcr.io/glatzel/<container>`. For example,
  `ubuntu-latest+ci-linux-release` uses `ghcr.io/glatzel/ci-linux-release`.
- Rows whose `pkg` starts with `_` are archived. They have no matching package
  directory and are skipped by the updater. Do not use an archived row as a
  template. `packages.yaml` is generated by CI; do not create or edit it.
- `lucifer/` is shared Python Selenium/Edge automation for downloading files
  from browser-driven sites. It is not a package and is protected. Existing
  consumers include `packages/furmark/download.py` and
  `packages/pureref/download.py`.

Useful template shapes:

- Simple recipe: `packages/7-zip/`
- Cross-platform scripts plus platform assets: `packages/codex/`
- Custom named build scripts, extra source files, and multiple outputs:
  `packages/rawspeed/`
- `noarch` package with a build script: `packages/skill-duckdb/`
- Static config files: `packages/codex-config/`

There are currently no tracked `.patch` files. If a change appears to require
a new patching layout, stop and ask rather than inventing one.

## How builds and updates work

- `.github/workflows/ci.yml` runs on pull requests (`opened`, `synchronize`,
  `ready_for_review`) and pushes to `main`. It derives the package matrix from
  `packages.csv`, compares changed files under `packages/<pkg>/`, and builds
  only the affected packages.
- On a pull request, CI builds but does not publish. The required PR check is
  `check-point`; any failed or cancelled build or formatting hook makes it
  fail.
- On a successful push to `main`, the same CI workflow sets the publish action
  and uploads the built package files to the `glatzel` channel on
  `prefix.dev`. Default build channels are `prefix.dev/glatzel` and
  `conda-forge`.
- `.github/workflows/update.yml` runs daily at 16:00 UTC and can be dispatched
  manually. It reads each maintained recipe's `extra.update`, creates an
  `update/<pkg>` branch, updates the quoted version and resets the build number,
  and opens a `chore` PR. Do not duplicate that work.
- Versions live in the recipe, normally under `context.version`, and are usually
  forwarded to `package.version`. Some recipes put the version directly under
  `package`. `build.number` is the conda build number.

## Add a package

1. Find the closest maintained package and copy its recipe and supporting-file
   structure. Do not copy an archived `_` row.
2. Create `packages/<name>/recipe.yaml` plus only the scripts or assets that
   package needs. Set the initial upstream version once, use build number `0`,
   include meaningful `tests`, and add `about` and `extra.update` sections based
   on the closest maintained recipe.
3. Add a row for `<name>` to `packages.csv`, preserving the header and platform
   matrix semantics above. Do not add columns.
4. Review the diff to confirm it contains only the new package and its CSV row.
5. Create `feat/<name>`, commit, push, and open a PR against `main`.
6. Use the Actions results to validate every matrix job. Fix only this package
   and its CSV row, push again, and repeat until PR CI is green.

## Fix a package

1. Open the failed `CI` run from the PR or the `main` push. Identify the package,
   platform matrix entry, job, step, exact failing command, and relevant log
   lines.
2. Inspect the closest working recipe and the target package's recipe and
   build scripts. Form the fix from those existing conventions.
3. Change only those files under `packages/<name>/`, or only that package's row
   in `packages.csv` if the matrix entry is the demonstrated cause. Do not bump
   a version or build number.
4. Create `fix/<name>`, commit, push, and open or update the PR against `main`.
5. Re-read the new workflow run until all intended matrix jobs and
   `check-point` pass.
6. If the cause is in a protected path, or would require changing automation,
   stop and report the evidence instead of working around it.

Changing `packages.csv` alone may not select an existing package for the build
matrix because CI detects package changes through `packages/<pkg>/**`. If a
matrix-only fix needs validation, explain that situation to the owner rather
than editing an unrelated package file to force a build.

## Reading CI results

Use the authenticated GitHub integration available to you. In the GitHub web
UI, open `Actions` and select the `CI` workflow for the branch or commit. When
`gh` is authenticated, the equivalent read-only commands are:

```sh
gh run list --workflow ci.yml
gh run view <run-id>
gh run view <run-id> --log-failed
```

For a PR, inspect all `rattler-build` matrix jobs and require `check-point` to
be green. For a `main` push that the owner explicitly asked you to monitor,
also inspect the `publish` step after the affected builds pass. CI access is
required: if GitHub Actions results are unavailable, report the blocker and
stop. Do not substitute a local build.

## Branch, commit, and PR conventions

- Use `feat/<pkg>` for a new package and `fix/<pkg>` for a repair. The automated
  updater reserves `update/<pkg>`.
- `main` requires a pull request and allows squash merges only. Open the PR
  against `main`; do not merge it.
- The repository uses Conventional Commits and checks the PR title. Recent
  package commits are normally unscoped and name the package in the summary:

  ```text
  feat: add rawspeed
  fix: solidcraft build memory on linux arm
  chore: update `rtk` from `1.0.0` to `1.1.0`
  ```

  Use an imperative, lowercase summary with no trailing period. Keep one package
  per PR. Use the same Conventional Commits format for the PR title.
- Stop after the PR is green and report the PR link, changed files, affected
  platforms, and CI result. The owner handles review and merge.
